# ADR-003: OAuth client_credentials, not authorization_code

**Date:** 2026-08-26
**Status:** Active
**Decision method:** AI proposal, human deferred — surfaced during self-review of the credential design

## Goal

Choose how the server authenticates to the v2 API.

## Context

Skilljar's own MCP server advertises, at
`mcp.skilljar.com/.well-known/oauth-authorization-server`:

```json
"grant_types_supported": ["authorization_code", "refresh_token"]
```

No `client_credentials`. It is a remote service acting on behalf of a browser user, so it needs
the interactive flow and a registration endpoint.

The **API's** authorization server is a different document at
`api.skilljar.com/.well-known/oauth-authorization-server`.

**Correction, 2026-08-27.** This ADR originally said that document "does offer
`client_credentials`". It does not — it advertises the same two grants:

```json
"grant_types_supported": ["authorization_code", "refresh_token"]
```

The decision is still right, but the evidence for it is a probe rather than the
metadata. `POST https://api.skilljar.com/v2/auth/token` with `grant_type=client_credentials`
and deliberately fake credentials returns:

```
HTTP 401  {"error":"invalid_client","error_description":"Invalid client credentials."}
```

— the grant was accepted and reached the credential check. A control with a nonsense
grant type returns `HTTP 400 invalid_request`, and the validator names the three it
accepts, `client_credentials` first:

```
"Input should be 'client_credentials', 'refresh_token' or 'authorization_code'"
```

So `grant_types_supported` is **incomplete for this endpoint**. That is the mirror image
of the discrepancy already recorded in `CLAUDE.md`, where the authorization server
advertises 88 scopes against 28 implemented: there the metadata runs ahead of the API,
here it runs behind it. In both directions, **probe beats docs** — including the
vendor's own machine-readable docs.

`scripts/check_upstream.py::check_client_credentials_grant` runs this probe on every
drift check. It needs no credentials, and if Skilljar ever does withdraw the grant it is
a total failure for this project — there is no browser here to run `authorization_code`
through — so it is worth detecting early.

The initial credential design copied `csa-google-workspace`'s interactive pattern — a `login`
subcommand, a browser consent flow, a cached token file — because that is what the reference
implementation does. Self-review found this was inherited rather than chosen.

## Decision

Use the `client_credentials` grant against `https://api.skilljar.com/v2/auth/token`. Configuration
is two environment variables (`CSA_SKILLJAR_V2_CLIENT_ID`, `CSA_SKILLJAR_V2_CLIENT_SECRET`). The
only cached state is a short-lived access token held in memory.

## Rationale

- Removes an entire subsystem: no browser, no redirect URI, no consent flow, no `login`
  subcommand, no token file on disk, no refresh-token custody.
- `csa-google-workspace` needed that machinery because Google's installed-app flow gave it no
  choice. Skilljar does give a choice.
- Fewer moving parts at startup, which matters because the OAuth consent flow writes to stdout and
  stdout is the JSON-RPC channel — the single most damaging failure mode for a stdio server.
- A machine credential also matches what the server *is*: an automation client, not a delegate
  acting as a specific human.

## Rejected alternatives

- **Mirror the official server's `authorization_code` flow** — would make us a remote service's
  shape without being remote, and reintroduces token-file custody for no gain.
- **Support both** — real cost, speculative benefit. Revisit only if a concrete need appears.

## Implementation

Implemented in `src/csa_skilljar/auth.py`. The token request sends `client_id` and
`client_secret` in the form body, which matches the server's advertised
`token_endpoint_auth_methods_supported: ["client_secret_post", "none"]`. The access
token is held in memory and nothing is written to disk.

**Still unverified:** whether the token request must carry a `scope` parameter, or
whether the grant returns everything the client was issued. The probe cannot tell,
because the credential check fires first. Settle it on first contact with a real
credential (`WAITING-FOR-002`).
