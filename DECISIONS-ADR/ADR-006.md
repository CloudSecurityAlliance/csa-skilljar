# ADR-006: Additive compatibility with the official tool surface

**Date:** 2026-08-26
**Status:** Active
**Decision method:** AI proposal, human approved

## Goal

Define what "reproduces the official server's tools" actually promises, given that the official
implementation has gaps we can see.

## Context

The official Skilljar MCP server's registry was enumerated directly: 73 tools. Reproducing the
*names* is easy. The complication is behaviour. Its `list_courses` accepts only `filter.title` —
**no pagination parameter at all** — while its `list_domains` accepts `page.cursor` and
`page.size`. On an org with a large catalogue, `list_courses` truncates with no documented way to
page.

So: replicate the flaw for compatibility, or fix it and diverge?

## Decision

**Additive compatibility.** Identical tool names and identical argument names to the official
server, plus *optional* parameters where theirs is missing something. A caller sending exactly
what the official server accepts receives exactly what it returns.

Parity is **tested, not claimed**: a stored snapshot of the official registry is diffed in CI, and
drift opens an issue.

## Rationale

- Pure replication would propagate a defect we can see, into a project whose value proposition is
  being better at the edges.
- Free divergence would break the drop-in promise, which is the reason to match names at all.
- Optional-with-matching-default is the standard way to extend an interface without breaking it.
- "Drop-in replacement" is a claim about someone else's software that changes without our
  involvement — it has to be a test, or it is rot waiting to happen.

## Rejected alternatives

- **Exact behavioural replication** — inherits `list_courses`' missing pagination on purpose.
- **Fix freely, document the differences** — a differences document nobody reads is not
  compatibility.
- **Do not match names at all** — loses the drop-in property, which is a genuine adoption argument.

## Implementation

Not yet implemented. Needs a stored registry snapshot plus a CI job that re-enumerates the live
official server when credentials are available.

## Amendment 2026-09-16 — additive compatibility has one deliberate subtraction

This ADR promises additive compatibility: every official tool name present, same arguments, extra
capability added alongside. **`register_oauth_client` is now an exception, and it is subtraction
rather than an omission.**

Skilljar's official server ships it **enabled**. Here it is an orange-line tool per
[CINO-PE DEC-016](https://github.com/CloudSecurityAlliance-Internal/CINO-Platform-Engineering/blob/main/DECISIONS.md):
reachable only when the `admin.credentials` capability is held **and** the tool is named in
`CSA_SKILLJAR_ORANGE`. A default install of this server cannot mint a credential; a default install
of theirs can.

**Why the promise bends here and nowhere else.** Minting a credential is control-defeating — a
caller that can do it escapes every gate above it, including the capability table that is supposed to
be constraining them. Gating it by profile alone is not a weaker control, it is an incoherent one,
because the agent that reaches the tool can edit the profile. The second grant exists to be held
somewhere the first is not.

`set_student_password` and `send_password_reset` are under the same rule, and both are CSA additions
rather than official tools, so neither affects the parity claim.

**What this costs, stated plainly.** The registry-diff test still passes — the tool is *registered*,
with the official name and arguments. What differs is whether a call succeeds on a default install.
So "drop-in replacement" remains true of the surface and is **no longer true of the behaviour** for
this one tool, and a consumer who scripted against the official server's `register_oauth_client`
will get a refusal naming the environment variable rather than a client.

That is the intended outcome. We would rather explain a refusal than explain how an agent minted a
credential nobody authorised.
