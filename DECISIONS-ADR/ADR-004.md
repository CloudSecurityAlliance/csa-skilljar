# ADR-004: No version marker in any tool name

**Date:** 2026-08-26
**Status:** Active
**Decision method:** AI proposal, human approved

## Goal

Decide whether a tool's name discloses which API serves it.

## Context

The server spans two APIs. An obvious convention would prefix v1-backed tools — `v1_list_webhooks`
— so callers know what they are touching. Skilljar has publicly reserved OAuth scopes for
webhooks, paths, assets, tags and commerce, so those capabilities are expected to move from v1 to
v2 over the project's life.

## Decision

No tool name ever contains a version marker. `list_event_subscriptions` is the name whether v1 or
v2 serves it.

## Rationale

- The version is an implementation detail of *ours*, not a property of the capability.
- A prefix would force a rename the day Skilljar ships the v2 endpoint, breaking every saved
  prompt, script and document that referenced the old name — a breaking change caused entirely by
  our own naming, for an upstream event that should be invisible.
- Retiring a v1 family is meant to be a non-event (ADR-002, GOALS "shrink"). A version-carrying
  name makes it a migration.
- Which backend served a call is still discoverable through `describe_capabilities` for anyone who
  needs it, rather than being encoded in a name everybody sees.

## Rejected alternatives

- **`v1_` / `v2_` prefixes** — honest about mechanism, wrong about durability.
- **Prefix only the v1 tools** — same rename problem, plus asymmetry that implies v1 tools are
  second-class.
- **Namespace by family instead** (`webhook_list`) — not a version marker, so not excluded by this
  ADR; rejected separately for consistency with the 73 official names we must match (ADR-006).

## Implementation

Not yet implemented. A test should assert no registered tool name matches `^v[0-9]_` or contains
`_v1_`/`_v2_`.
