# ADR-005: Two-layer gating — profile registers, policy executes

**Date:** 2026-08-26
**Status:** Active
**Decision method:** Collaborative — AI proposed registration-gating, self-review found the flaw, revised design accepted

## Goal

Control both what an install is *permitted* to do and what it *costs in context*, without the two
controls undermining each other.

## Context

The full surface is roughly 120 tools. At the ~100 tokens per tool that CINO-Platform-Engineering
measures for always-on context, registering everything costs ~12k tokens before anyone asks a
question, and degrades tool selection.

`csa-google-workspace` gates at the `Backend` seam and keeps every tool registered. The initial
proposal here diverged: let a profile control *registration*, so disabled tools cost nothing.

Self-review found the flaw. A tool the model cannot see becomes a capability the user never learns
exists — the model says "this server does not support webhooks" when the truth is one profile
change away. That is the same failure this project works hard to avoid for credentials.

## Decision

Both layers, doing different jobs:

- **Profile controls registration.** An unregistered tool costs no context. This answers the
  120-tool problem.
- **`PolicyBackend` controls execution**, wrapping the backend seam. Fails closed: a method with
  no declared gate is refused, not delegated. Library embedders get the same guarantee as MCP
  clients.
- **`describe_capabilities` is always registered**, reporting what exists but is not enabled.

Profiles: `parity` (default) · `authoring` · `people` · `reporting` · `operations` · `admin` ·
`full`. Composable. The configuration is the complete permitted list, never a delta, and cannot be
widened in-band — no tool changes it.

## Rationale

- Registration-gating alone trades one legibility problem for another.
- Seam-gating alone does not solve context cost.
- `describe_capabilities` restores discoverability for about 100 tokens, which is the cheapest part
  of the design.
- Named profiles because nobody composes a capability list correctly under time pressure, and
  everybody can pick a word.

## Rejected alternatives

- **Registration-gating only** (the original proposal) — hides capability from the one party who
  could enable it.
- **Seam-gating only** (strict `csa-google-workspace` parity) — correct on security, ignores that
  this server has roughly four times the tool count.
- **Ship fewer tools** — the project's entire purpose is coverage.

## Implementation

Not yet implemented. The capability expectation matrix must be **hand-written**, never derived
from the gate table — deriving it tests the table against itself and passes regardless of content.
