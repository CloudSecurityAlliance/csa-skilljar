# ADR-002: v2 owns every capability v2 has; v1 only fills gaps

**Date:** 2026-08-26
**Status:** Active
**Decision method:** Human directive — Kurt specified the routing rule; AI had proposed a fallback design

## Goal

Decide which API serves a capability that both APIs implement, and whether the server may fall
back from one to the other.

## Context

Seven capabilities exist in both APIs: courses, domains, groups, lessons, question banks, quizzes,
web packages. The two are not interchangeable — v2 is JSON:API with cursor pagination and no total
count; v1 is a flat Django-REST envelope with cursor pagination *and* a total count. Field names
differ (`hidden`/`is_hidden`, `html`/`question_html`), and v2 puts `id` in the resource envelope
rather than in attributes.

The AI had proposed announced fallback: prefer v2, drop to v1 on failure, and mark which API
served the response. Kurt rejected the fallback entirely and specified single ownership.

## Decision

**v2 owns every capability v2 has. v1 is used only for capabilities v2 lacks.** No fallback, no
dual-routing, no preference order — each capability has exactly one owner.

## Rationale

- A fallback hands the caller a different data shape under failure conditions, which is when they
  are least equipped to notice.
- Single ownership means no tool-name collisions, so the namespace stays flat.
- Migration becomes trivial: when a capability lands in v2, one backend reference changes and no
  tool signature moves.
- The rejected design's mitigation — annotate which API served the response — pushes the problem
  onto every caller instead of solving it.

## Rejected alternatives

- **Announced fallback** (the AI's original proposal) — the annotation is only useful to a caller
  who handles both shapes, which is exactly the burden the project exists to remove.
- **Prefer v1 for richer responses** — v1 does return a total record count that v2 omits. Not
  worth splitting ownership by field-level advantage.
- **Expose both and let the caller choose** — doubles the tool surface and leaks the seam.

## Implementation

Not yet implemented. Enforced structurally: each capability is registered by exactly one
`register_*_tools` producer bound to one backend.

## Related decisions

ADR-004 (no version marker in tool names) is what makes migration invisible to callers.
