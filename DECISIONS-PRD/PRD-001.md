# PRD-001: Scope — reproduce the official surface, then fill the v1 gap

**Date:** 2026-08-26
**Status:** Active
**Decision method:** Collaborative — scope negotiated across a design session, with the AI probing upstream and the human setting boundaries

## Problem

Skilljar exposes two REST APIs. Their official MCP server covers only v2 — 73 tools, verified by
enumerating its live registry. The v1 API is considerably larger (340 operations against v2's 82)
and is today the only route to per-lesson learner progress, webhooks, asset upload, learning
paths, instructor-led training and commerce. None of that is reachable from any AI client.

CSA runs its training on Skilljar and hits these gaps in ordinary work.

## Audience

1. **CSA training and certification staff** (primary) — course authoring, exam item banks,
   enrolment, progress reporting.
2. **Any Skilljar customer** hitting the same v2 gaps — the package is public and Apache-2.0.
3. **Python integrators** who want the library without the MCP server. The library is a product in
   its own right, not an implementation detail.
4. **CINO-Platform-Engineering** as a research consumer — CSA's third MCP server and the first
   over two API generations.

## Purpose

One tool surface over both APIs, where which API serves a capability is invisible to the caller,
and where the project **shrinks** as Skilljar builds v2 out.

## Requirements

- Reproduce all 73 official tool names with identical argument names (ADR-006)
- Add the v1-only families, ordered by usage evidence (ADR-007)
- Run locally over stdio; credentials never leave the operator's machine
- Two independent, individually optional credentials; the server starts with either, both or
  neither and says what is available
- Every auth failure produces one distinct, actionable remedy
- Capability profiles gate what an install exposes and what it may execute (ADR-005)
- The whole surface testable offline with no network and no credentials
- Detect upstream drift automatically rather than by documented ritual

## Out of scope

- **Webhook receiving.** We manage subscriptions; we are not an HTTP endpoint.
- **Caching.** Sessions are live and multi-actor; a self-invalidated cache goes stale.
- **Cross-API composite writes.** v2 has a batch envelope with per-item results; v1 has nothing
  equivalent. Multi-step writes stay the caller's business.
- **Catalog page-building.** ~60 v1 operations for a page builder an agent should not drive.
- **v1 families with no data in the reference org** — license packages, progress tokens,
  multi-session events, access-code pools.
- **Surviving upstream change.** We detect drift and report it; we do not paper over it.

## Success criteria

- All 73 official names implemented, verified by registry diff against the live server
- `pip install csa-skilljar` from PyPI with build attestations
- A CSA training workflow that previously needed manual steps runs unattended
- At least one v1 family retired because v2 shipped it

## Rejected alternatives

- **Complete 1:1 tool coverage of both APIs** — 422 tools, roughly 40k tokens of always-on
  context. Honest to "does everything", unusable in practice. Resolved instead by profiles
  (ADR-005) plus job-shaped v1 tools.
- **CSA training pipeline only** — ~15 tools, narrow and useful, but forfeits the drop-in
  property and the community audience.
- **Wait for Skilljar to ship v2 coverage** — they have reserved the scopes but published no
  date, and the endpoints 404 today. Recorded as `WAITING-FOR-001` rather than as a reason not to
  build.
- **Contribute to the official server instead** — closed, first-party, no third-party contribution
  path.

## Assumptions

- v1 remains available and supported for the project's useful life. It is Skilljar's larger API
  and their documentation treats it as current.
- Skilljar's v2 will continue to grow. Their scope catalogue advertises 88 scopes against 28 in
  the published spec — evidence of intent, not a commitment with a date.

## Open questions

- Should the integration suite use the broad organisation key, or a narrower credential?
- Is the always-on cost of a demonstration tool worth it at this tool count?
