# Threat Model: csa-skilljar

## 1. System context

`csa-skilljar` is a Python library plus a **local stdio MCP server** wrapping both of Skilljar's REST APIs — the older v1 and the newer v2 — behind one flat tool namespace. At the reviewed revision (`280c8e8`, v0.13.0) it registers **112 tools across 23 families**, ~10,200 lines in `src/` with ~8,100 lines of tests. Skilljar is Gainsight's customer-education platform; CSA runs its training and certification programmes on it, and the reference organization holds **42,669 learner records**. Development history is extremely short: 47 commits on `main` (130 across all refs), effectively one author, everything written between 2026-08-26 and 2026-08-29 — 77 hours.

The architecture is `MCP tools → PolicyBackend → SkilljarClient → {V2Backend | V1Backend | FakeBackend}`, with one absolute routing rule (ADR-002): v2 owns every capability v2 has, v1 fills only the gaps, no fallback and no dual-routing, enforced by a test asserting the two backends' method sets are disjoint. `SECURITY.md` frames the risk correctly and unusually plainly: *"It listens on no port, is not deployed, and stores nothing. The trust boundary is the operator's own machine. So the question is not 'what can reach us' but **what can the credentials we hold reach, and who can influence what we do with them.**"*

**Two independent credentials, with wildly unequal containment.** The v2 credential is an OAuth `client_credentials` pair exchanged for a 900-second access token held in memory only — no token file, no refresh-token custody, no browser. It is organization-bound and **per-operation scoped**, with a local pre-check that refuses an impossible call before any network traffic. The v1 credential is an **organization API key** used as HTTP Basic with the key as username and an empty password. Per the maintainer, Skilljar issues v1 keys as either read-only or full-access with **no finer scoping** — so the two statements in the repository (`SECURITY-RESOURCES.md` calling the testing key read-only, and `v1backend.py:44-51` saying keys cannot be narrowed) are both true: the choice is binary, not scoped. Whichever variant is issued, one key reaches every learner record in the organization, and nothing in this codebase can narrow it. That asymmetry is why ADR-002 prefers v2 wherever both APIs can serve, and it is the single most important fact in this model.

**Three control layers bound every threat below, and the first is assumed.** (1) **Skilljar itself** — the credential's actual scopes, set in the Skilljar Dashboard and not in version control; the platform's own enforcement, which remains authoritative for every call; and whatever the platform does to content on render. This layer is where the strongest control lives and none of it is in this repository. (2) **The MCP client** — per-tool enablement and the operator's approval mode, neither mandated by the MCP specification and neither observable from this codebase. (3) **This server** — 19 capabilities across 8 composable profiles, enforced fail-closed at the `Backend` seam so an undeclared method is refused rather than delegated, with `parity` (reads only) as the default and the policy unwidenable in-band. Layer 3 is genuinely well built; it is not the primary layer and does not claim to be.

**Operators hold Skilljar administrative access independently of this tool**, so nothing here is privilege escalation — every action is one the operator could perform directly. The delta is *who decides*: a lesson body, a quiz question, a learner's free-text signup answer or a course rating is attacker-influenceable text, and the same agent that reads it holds tools that erase learner PII, reset passwords, delete content, publish courses and write HTML into a learner-facing portal. `SECURITY.md` names prompt injection through course content as the primary risk and says the containment is the operator's credential scoping, not the model's judgement. The training portal is sign-in gated beyond course descriptions, so content written into it renders for **authenticated learners** rather than the anonymous internet.

**One rating in this model is conditional and cannot be resolved statically.** T1 assumes Skilljar does not sanitise `content_html` on render. Nothing in this repository can establish that, the maintainer does not take the vendor's documentation for it, and settling it requires an empirical round trip — write a payload, read it back, observe the rendered page — against an isolated course. Until that is done, T1's impact is stated as the upper bound with the assumption named.

## 2. Assets

| asset | description | sensitivity |
|---|---|---|
| A1 v1 organization API key | `CSA_SKILLJAR_V1_API_KEY`. HTTP Basic, key as username, empty password (`v1backend.py:57-61`). No token, no expiry, no scopes — the key *is* the authorization, organization-wide, and Skilljar offers read-only or full with nothing between. Reaches every learner record, every asset, all commerce, every webhook configuration including three classes of third-party secret. Stolen, it works from any host unless an IP allowlist was set elsewhere. | critical |
| A2 v2 client id + secret | `CSA_SKILLJAR_V2_CLIENT_ID`/`_SECRET` (`mcp/_config.py:25-26`), exchanged for a ~15-minute JWT (`auth.py:77-106`). Blast radius equals the scopes that client was issued — the narrowable credential, and the one the docs push first. Access token in memory only; never written to disk. | critical |
| A3 Bulk learner PII corpus | 42,669 real people. Names, emails, enrolment history, per-course progress, quiz attempts and scores, certificates with a public verification code, free-text course ratings, signup-field values (frequently employer and job title), group memberships, ILT registrations. Bulk paths: `list_students`, `list_enrollments`, `list_vilt_registrations` (name+email per row), `list_signup_field_values`, `list_ilt_instructors`. **All granted by the default `parity` profile.** | critical |
| A4 Integrity of the learner-facing portal | What a learner's browser renders. `create_lessons`/`update_lessons` accept `content_html` and `description_html`; `questions.py` accepts four more HTML fields. `publish_courses` puts the result on a customer-facing domain. This is the asset T1 compromises. | critical |
| A5 Learner account-takeover primitives | `set_student_password` (learner not notified, old password dead), `send_password_reset` (mails a real person), `deactivate_student`, `anonymize_student` (**irreversible** PII erasure, no undo, no support path). All `people.destructive`, granted by no profile but `full`; the two worst also require `confirm=True`. | critical |
| A6 Integrity of completion records and certificates | `complete_enrollments` marks enrolments complete, can issue a certificate, and with `send_notifications=true` emails learners that they passed. Completion is reversible in-band; **the email is not**, and a certificate an employer already verified via its public code cannot be un-quoted. | critical |
| A7 The agent's own instruction stream | Third-party text reaching model context: lesson `content_html`, quiz question and answer text, learner free-text ratings (`list_course_ratings` is **unpaginated** — every rating a course ever received in one call), signup-field values, group names and `rule_email_domains`, course descriptions. The only control is prose. | high |
| A8 The OAuth client estate | Enumerate every credential and its scopes, mint a new one with a one-time secret returned into model context, widen scopes, rotate (breaking every service on the old secret), deactivate, revoke refresh tokens. All eight tools — **including the reads**, deliberately, since enumeration is reconnaissance — behind `admin.credentials`. | high |
| A9 Webhook receiver secrets | `/v1/webhooks` returns, in plaintext, a 32-char `X-Skilljar-Secret` header value, an `auth=` token inside `target_url` query strings, and `basic_auth_password` per row. These authenticate Skilljar *to* CSA's own downstream services. The one raw-secret path in the codebase, and it is correctly wrapped. | high |
| A10 Presigned S3 asset download URLs | `get_asset` returns a `download_url` that is a **bearer capability, not a reference** — no Skilljar credentials, ~60 minutes, verified live by the authors. Anyone who reads it in a transcript, ticket or screenshot downloads the course file. No control in this repository reaches it. | high |
| A11 Group membership and course visibility | Membership grants or revokes course access. `delete_groups` is a **hard** delete cascading to memberships and visibility overrides, so deleting a group can silently revoke access learners currently hold. | high |
| A12 Publishing state / customer-visible storefront | The only family whose effects reach beyond signed-in learners. `open_access` allows anonymous access; `visible_on_catalog` lists publicly. Unpublish frees the slug and republish reassigns it, so a course can return at a different address. | high |
| A13 Assessment content and answer keys | `get_question` returns answers *and which are correct* — the exam key — under `content.read`, which `parity` grants. Answers are immutable on update, so changing them means delete-and-recreate. | medium |
| A14 Commerce and purchase records | Promo codes (13,708 in the reference org), pools, offers, training-credit codes, and one real person's transaction via `get_purchase`. Read-only by decision (ADR-007) with a test asserting the module never grows a write tool. Unlike v2 tools, these return **raw upstream rows** with no field allowlist. | medium |
| A15 Skilljar API quota and tenancy availability | **No 429 handling, no `Retry-After`, no backoff, no client-side throttle exists anywhere in `src/`.** Amplifiers: `list_learner_progress` and `list_course_ratings` are unpaginated, and v1 honours `page_size=1000`. | medium |
| A16 Downstream embedder trust | Ships as a library. `SkilljarClient.__init__` accepts a bare `Backend` as well as a `PolicyBackend`, and `client.policy` returns `None` when unwrapped — so `policy.py:5-8`'s promise that "a library embedder gets the same guarantee as an MCP client" holds for the server, not the library. | medium |

## 5. Deprioritized

| threat | reason |
|---|---|
| SSRF via a redirected API base URL | Ruled out and specifically checked. `Settings.base_url` is a dataclass field with a hardcoded default and `settings_from_env` reads exactly four keys, none of them a base URL — there is no `CSA_SKILLJAR_BASE_URL`. Nothing in the process environment can redirect either credential to an attacker host. TLS verification is never disabled, and `follow_redirects` is never set so httpx's default of `False` applies, meaning a 3xx cannot replay the `Authorization` header to another host. |
| Cross-principal session access, DNS rebinding, WebSocket origin validation and the other `mcp`-SDK transport advisories | Not applicable twice over. All are below the declared `mcp>=2.1` floor, **and** the server constructs stdio only — `mcp/cli.py:59` is the single `transport=` site in `src/`. There is no listener to rebind against and no session to ride. Worth recording as an invariant to defend rather than an implementation detail: adding an HTTP transport would convert an unscopeable organization-wide credential into a network-reachable one, and this advisory class is precisely about transports serving sessions without verifying the principal. |
| Unverified JWT signature as an authorization flaw | Investigated and refuted. `auth.py:27-50` decodes claims without verifying the signature, deliberately and with the reasoning written down: it is the client's own token, obtained via `client_credentials` from Skilljar's token endpoint, and the claims feed exactly two things — `exp` for local refresh timing and `scope` for a pre-check that can only *refuse* early. | SQL, command, LDAP, XPath and template injection | No such interpreter is reached. No database, no ORM, no template engine on any data path, and no `subprocess` anywhere in `src/`. |

## 6. Open questions

- **Does Skilljar sanitise `content_html` on render?** The single most consequential unknown in this model, and T1's rating depends entirely on it. The maintainer does not take the vendor's documentation for it, which is the right instinct. Settling it needs an empirical round trip — write a payload, read it back through the API, and observe the rendered page — against an isolated, unpublished course with guaranteed teardown. Until then T1 is stated at its upper bound with the assumption named. Note this is also the first concrete test case for the API-server-as-test-harness idea: the audit has framed the question, and answering it needs a third observation point the MCP server cannot provide.
- **Which `CSA_SKILLJAR_PROFILE` do the deployed configurations actually set?** Several ratings turn on it — T9 (`authoring` can delete) only bites where `authoring` is used, and T4/T5/T6/T21 are all scored on `full` being rare. The maintainer confirms operators are training staff with Skilljar admin access, which settles the actor question but not the configuration.
- **Which v1 key variant is deployed, and against which organization?** The maintainer confirms Skilljar offers read-only or full with no finer scoping, and that the read-only variant is what has been used. Confirming that is what bounds T3 and T7 to disclosure rather than damage. Related, and still open in the repository's own TODO: the dev v2 client holds four authoring write scopes (`courses:write`, `lessons:write`, `quizzes:write`, `question-banks:write`) against the production organization that nothing uses, with `WAITING-FOR-003` recommending it be re-issued read-only.
- **Has any write tool ever executed against a real Skilljar organization?** The repository states plainly that none has, and records it so the absence is not mistaken for an absence of testing. That means every write path in this model is reasoned rather than observed.
- **Do the deployed MCP clients honour `readOnlyHint` for auto-approval, and which tools are enabled?** Per-tool enablement is the strongest control available for T16 and T17 and it lives entirely in client configuration this repository cannot see.
- **Are the externally-enforced controls actually in place?** Specifically: does the `pypi` GitHub Environment exist *with* a required-reviewer rule (T22); is branch protection configured; is CodeQL default setup enabled, given `SECURITY-RESOURCES.md` discusses a live CodeQL alert while no workflow file exists?
- **Is the training portal's public surface limited to course descriptions?** The maintainer reports sign-in gating beyond that. Course descriptions being anonymously readable matters because `courses.py` is one of the tool families with no untrusted-content marking.
- **Should `PROFILES` gain a bulk-read/single-read split?** T13 records that the default profile's disclosure reach is identical to `full`'s. There is currently no intermediate posture between "read the whole learner corpus" and "everything".
