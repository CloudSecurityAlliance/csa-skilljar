They are shaped differently

Before comparing resources, these conventions differ everywhere

Authentication

v1HTTP Basic — API key as username, empty password. Also a bearer token scheme. v2OAuth 2.0 bearer JWT. client_credentials via /v2/auth/token, plus RFC 7591 dynamic registration — which is what lets MCP clients self-register.

Authorization

v1All-or-nothing. An API key reaches every endpoint. v228 scopes, declared per operation as x-required-scope (any-of). Destructive actions are isolated: students:anonymize, students:deactivate, students:manage-password.

Pagination

v1Offset style — count, next, previous, results. v2Cursor style — data, meta, links, has_more, next_cursor, included. No total count.

Writes

v1One resource per call. POST /v1/quizzes, PATCH /v1/quizzes/{id}. v2Batch by default — 44 of 82 operations write at collection level. PATCH /v2/quizzes/ takes many items and returns 207 with per-item success/failure and a summary.

Response shape

v1Flat objects. id sits alongside the data. v2JSON:API — resource / attributes / relationships. id moves to the envelope, so it disappears from every attribute diff below.

External identity

v1None. You keep your own ID mapping table. v2external_id on courses, lessons, quizzes, banks, questions, students, published courses, domains and web packages — your key, stored on their object.

Consequence for tooling: nothing written against v1 ports to v2 mechanically. Auth, pagination, request envelope and write granularity all change together. Treat them as two integrations, not two versions.

What this means for a CSA integration

Reading the map for training-content work
  • BANKSQuestion banks are fully supported in v2 — and are better there. v1 can only read a bank's questions and delete them; it has no way to add a question to a bank or bind a bank to a quiz. v2 does all of it, including reweighting the binding. For reusable exam-item pools this reverses the expected verdict.
  • GAPSThree surfaces are absent from v2 with no workaround. Webhooks (17 v1 operations, zero in v2), instructor-led and virtual sessions, and the entire commerce stack — purchases, offers, promo codes, license packages, training credits. Learning paths are also v1-only.
  • REPORTINGCourse-level reporting is better in v2; lesson-level is v1-only. v2 enrollments carry score, max_score, progress_status, success_status, completed_at and has_certificate. But nothing in v2 reports per-lesson progress.
  • SCOPESLeast privilege is achievable on v2 and impossible on v1. An authoring credential can hold courses, lessons, quizzes and question-banks scopes and no students:* at all — which closes the prompt-injection path from "summarize this lesson" to "anonymize this student" at the token rather than relying on agent judgment. A v1 key cannot be narrowed.
  • BOTHA complete integration needs both APIs. v2 for authoring, enrollment, reporting and anything an agent touches; v1 for webhooks, paths, ILT and commerce. Note that v1 keys and v2 clients are separate credentials with separate trust levels.
